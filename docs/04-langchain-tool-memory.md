# POC 04: Manually Executing LangChain Tools

## Purpose

Demonstrate the tool-calling round trip between an LLM and application-managed
tools. The model decides which tool can help and returns a structured request;
the application selects and runs the implementation, then returns the result
to the model so it can produce a final answer.

## Problem

An LLM can identify a tool and supply arguments, but that request does not run
the Python function by itself. The application must safely map the requested
tool name to an implementation and manage the messages that connect the model
call to the tool result.

## Solution

The POC binds two tools to the Groq chat model:

- `calculate_word_count`, a custom Python tool.
- `wikipedia`, a LangChain Wikipedia query tool.

`ask_llm_manually()` manages the interaction:

1. It sends the user's prompt to the tool-enabled model.
2. It inspects the response's `tool_calls`. If there are none, it prints the
   model's direct response.
3. For each requested call, it reads the tool name and arguments, looks up the
   executable in `tool_map`, and invokes it.
4. It wraps each result in a `ToolMessage` with the matching tool-call ID.
5. It sends the original user message, the model's tool-call response, and
   the tool messages back to the model. The model uses that result to produce
   the final answer.

The application—not the model—executes the Python code and controls which
tools are available. An unregistered tool name raises an error instead of
being executed.

## How to Run

From the project root, install dependencies and configure `GROQ_API_KEY` in
`.env`, then run:

```bash
uv sync
uv run python "poc04_langchain_tool_manully_calling copy.py"
```

The script sends two example prompts: one for the custom word-count tool and
one for Wikipedia. Wikipedia requires network access.

## Sample Output

The exact wording and Wikipedia content vary by model response. A word-count
run follows this shape:

```text
User Prompt: "Count the words in this sentence: Manual tool binding gives you full control."
-> LLM wants to use a tool.
   [LLM Request] Tool Name: calculate_word_count
   [LLM Request] Tool Arguments: {'text': 'Manual tool binding gives you full control.'}
   [User Execution Result]: 7
   [LLM Final Answer]: The sentence contains 7 words.
```

The Wikipedia example similarly prints the requested tool and query, the
Wikipedia result, and then a final response generated by the model from that
result.

## Expected Output

For each prompt, expect either:

- A tool-call request, the application-executed result, and a final LLM answer
  based on the returned tool result; or
- A direct LLM response if the model decides no tool is needed.

For the word-count prompt, the sentence has seven words. Wikipedia results
depend on the live service and may change.

## Lessons Learned

- Tool binding exposes tool names and argument schemas to the model; it does
  not execute tools.
- The application owns the dispatch step: it maps a model-requested name to a
  real implementation and passes the supplied arguments.
- Tool-call IDs connect each `ToolMessage` to the corresponding request.
- The model needs the tool result in the conversation to incorporate it into
  a final answer.
- Explicit dispatch makes the execution flow visible and lets the application
  control which tools can run.

## Limitations

- This is a small, fixed example rather than a general-purpose tool runner.
- The tool registry must be kept in sync with tools bound to the model.
- Tool execution and API errors are not retried or recovered from.
- Wikipedia requires network access and its returned content may be
  incomplete, unavailable, or out of date.
- The example does not persist conversation history between prompts or runs.

POC 05 uses LangChain's `create_agent` to automate the tool-selection,
